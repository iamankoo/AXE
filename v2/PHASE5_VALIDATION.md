## Per-installation device identity

Each AXE installation creates its own ECDSA P-256 key pair on first run (private key protected by DPAPI). The device id is the
SHA-256 of its public key. The public key is registered with the request, copied onto the grant, and every authorization check
carries a signature over `axe-device-proof|nonce|grantId`. A copied grant is useless on another installation: the server answers
`device`. This replaces the earlier client-only device hash (finding F6, now closed). Covered by 6 + 7 backend tests (two and
more installations, copied grants, replayed/forged proofs, independent expiry and revocation) and 4 Windows tests. A fresh key per
harness run showed distinct identities against production.

Three token-registration tests had failed once while the machine was saturated by parallel builds. **Cause (reproduced
by saturating the CPU):** the `before` hook's setup request failed at the transport level (`fetch failed`), which fails every
test in that file. **Fix:** `tests/net-helper.mjs` retries only idempotent setup calls (GET/HEAD and password sign-in) and the
`supabase status` lookup; it never retries the Edge Function calls under test and never retries anything that received an HTTP
answer, so it cannot hide a wrong status or body. No test or assertion was removed or weakened.

## Security audit: findings and outcome

| # | Finding | Severity | Outcome |
| --- | --- | --- | --- |
| F1 | Invitation-code guesses were unmetered | Medium | **Fixed**: 20 attempts/hour/network, right or wrong (no oracle) |
| F2 | `AXE_HASH_SECRET` defaulted to empty: hashes silently unkeyed | Medium | **Fixed**: fails closed (generic 500); verified live |
| F3 | `AXE_PUSH_TEST_SINK_URL` accepted any URL | Medium | **Fixed**: loopback only |
| F4 | Rate-limit key used the client-controlled first `x-forwarded-for` entry | Medium | **Fixed** |
| F5 | Acknowledgement endpoint unmetered; sign-ups enabled in `config.toml` | Low | **Fixed** (and sign-ups disabled in production, verified) |
| F6 | Server could not verify device binding | Info | **Fixed** by per-installation device keys |
| F7 | Test setup could fail wholesale on a transport timeout | Low (test infrastructure) | **Fixed** (retry helper, above) |
| W1 | Release Windows build could embed a developer `server.json` | High (config) | **Fixed**: Release refuses a development config; the build script also rejects non-HTTPS/localhost, extra fields and service keys |
| W2 | Malformed embedded config threw at startup | Medium | **Fixed** (fails closed) |
| A1 | Android release accepted loopback/HTTP and placeholder Firebase ids | Medium | **Fixed** (release guards) |
| A2 | No release signing mechanism | Low | **Added** (git-ignored `keystore.properties`, keystore kept outside the repository) |
| A3 | Date formatters fixed at startup | Low | **Fixed** |
| S1 | An invitation code from the first commit is public in git history | Medium | **Cannot be removed from history. Production uses new codes only; never reuse the old one.** |
| S2 | Own scripts and docs named invitation codes / a fragment of the admin password | Low | **Fixed** (replaced with generic wording) |

Secret scan of the working tree (tracked + untracked, non-ignored): no private keys, no service-account material, no Supabase
tokens, no JWTs, no admin password, no invitation codes. Remaining matches are variable *names* (`AXE_HASH_SECRET=`, `service_role`,
`"private_key"` field names in the FCM verifier) with no values. Release artifacts: the APK contains none of the secret strings
(only the public project/Firebase identifiers and the production URL); the Windows publish output is scanned by the build script.

## Known limitations

* The installer is unsigned; the APK is signed with a self-managed key (back up `axe-admin-release.jks`: it cannot be recovered).
* Production data deletion, real-duration expiry, real clock changes and the real WPF/WebView2 window were not tested against production (see above).
* Several phone-side behaviours (tap/deep link, stale, foreground, killed app) are owner-reported, not independently observed.
* The production non-admin check was not run (no second production user can exist while sign-ups are off).
* Free-tier Supabase projects pause after inactivity.

## Verdict

**Production deployment, Firebase/FCM delivery, Windows <-> Supabase <-> phone approve/reject, device-bound grants and the release
artifacts: done and verified as listed. Items marked NOT TESTED or USER-REPORTED above remain open or unverified by the build
session**, so this report does not claim every mandatory validation was independently performed.
